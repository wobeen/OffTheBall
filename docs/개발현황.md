# 개발 현황

## 현재 상태 — 2026-10-01

- GitHub 저장소는 공개 상태이며 Google Colab에서 별도 토큰 없이 복제할 수 있다.
- `OffTheBall_Colab.ipynb`은 `main` 브랜치를 `/content/OffTheBall`에 얕게 복제한다. 기존 작업 폴더는 첫 셀을 다시 실행할 때 삭제 후 재생성한다.
- Git 복제는 사용자명 입력을 기다리지 않으며, 한 번에 45초씩 최대 두 번 시도한 뒤 실제 오류를 출력한다.
- Colab은 T4 GPU에서 녹화 영상을 전체 분석하고 결과 영상과 JSON 기록을 ZIP으로 내려받는 용도다. Windows 데스크톱 UI, 화면 영역 캡처, 태블릿 MJPEG 실시간 입력은 로컬 앱에서 사용한다.
- 로컬 앱은 YOLO11n·ByteTrack 선수 탐지/추적, 팀 A/B 분류, 그라운드 경계 필터, 시간바 탐색·일시정지, 전술 보드와 간격 지표, 이벤트 기록을 지원한다.
- 수동 및 자동 경기장 보정 기반 좌표와 기준 포메이션 저장·비교 기능이 포함되어 있다. 공 소유권과 공격·수비 상황을 자동 확정하는 기능은 아직 제공하지 않는다.
- Colab 복제 수정(`codex/fix-colab-clone`)은 PR #4로 `origin/main`에 반영됐다. 최신 노트북은 `main`에서 받으면 된다. 이 작업 브랜치에도 2026-10-01에 `origin/main`을 병합해 반영했다(전체 회귀 98개 통과).
- 최근 기록된 전체 회귀 검증은 96개 통과다. 이번 갱신은 문서만 변경한다.

### 브랜치 운영 규칙 (2026-10-01 확정)

- 상시 브랜치는 `main`, `develop`, `hotfix` 세 개만 둔다. GitHub 기본 브랜치는 `develop`이다.
- `main`: 안정 기준. 직접 커밋하지 않고 `develop` 또는 `hotfix`에서 PR로만 갱신한다.
- `develop`: 업데이트용. 모든 기능 브랜치의 병합 대상이다. 검증이 끝나면 `main`으로 PR을 올린다.
- `hotfix`: 급한 수정용. `main`에서 따서 `main`으로 PR을 올리고, 병합 후 `develop`에도 반영해 둘이 어긋나지 않게 한다.
- 기능 브랜치(`codex/<이름>`)는 `develop`에서 따서 `develop`으로 PR을 올리고, 병합 후 삭제한다. Codex 등 자동 도구가 만드는 브랜치도 같은 규칙을 따른다.
- PR 병합 방식은 squash로 통일한다. 커밋과 브랜치 생성, push, PR 병합은 사용자가 직접 한다.
- 아래 B0~B7 브랜치는 모두 `develop`에서 딴다.

### 구현 단위 4 — 키포인트 보정 시간 안정화와 stale 좌표 차단

상태: 구현 및 자동 테스트 완료, 사용자 커밋 대기

#### 수정한 코드와 이유

- `src/offtheball/calibration_state.py` 신규 추가
  - 프레임마다 생성되는 `KeypointCalibration` 후보를 받아 현재 보정으로 채택하거나 거부하는 `TemporalCalibrationState`를 구현했다.
  - 새 후보의 inlier 영상 좌표 중 이전·새 보정 영역에 모두 포함되는 점을 골라, 동일 픽셀이 두 보정에서 몇 미터 차이로 투영되는지 계산한다.
  - 공유점의 중앙 투영 차이가 기본 8m를 넘으면 갑작스러운 보정 점프로 보고 거부한다. 공유점이 기본 4개보다 적어 비교 근거가 부족한 후보도 거부한다.
  - 새 후보가 없거나 거부될 때 마지막 보정의 age를 증가시키며 기본 30프레임까지만 재사용한다.
  - 재사용 한도를 넘으면 상태를 `stale`로 바꾸고 `project()`가 전부 `NaN`을 반환한다. 오래된 좌표가 현재 선수 위치처럼 전술 보드와 지표에 남는 것을 막기 위한 변경이다.
  - stale 이후에는 장면 전환으로 크게 달라진 정상 후보도 새 기준으로 다시 채택할 수 있다. 이전 보정과 계속 비교해 복구가 영구 차단되는 문제를 피한다.
  - 입력 해상도 변경은 조용히 재사용하지 않고 명시적으로 재보정을 요구하며, `reset()`으로 모든 시간 상태를 비울 수 있다.
  - 실제 프레임을 갱신하는 메서드와 혼동하지 않도록 후보 입력 메서드는 `update()`가 아닌 `observe()`로 분리했다.

- `src/offtheball/analysis.py`
  - 시간 안정화기가 계산한 `projection_jump_m`를 공통 보정 진단과 향후 `frames.jsonl`에 보존하도록 진단 스키마를 확장했다.
  - 값이 무한대나 `NaN`이면 기존 진단값과 동일하게 `null`로 정규화한다.

- `tests/test_calibration_state.py` 신규 추가
  - 최초 정상 후보와 작은 카메라 이동 후보 채택을 검증한다.
  - 큰 투영 점프 거부 후 이전 보정이 유지되는지 검증한다.
  - 후보 누락 중 제한 프레임까지 좌표를 재사용하고 한도 초과 즉시 좌표를 차단하는지 검증한다.
  - stale 상태에서 크게 달라진 새 장면 후보를 받아 복구하는지 검증한다.
  - 공유 영역 부족, 해상도 변경, 잘못된 후보 타입과 설정값을 거부하는지 검증한다.
  - `AnalysisSession`에 실제 보정 객체로 연결했을 때 active 상태에서 `field_xy`가 생성되고 stale 상태에서 `None`으로 사라지는지 검증한다.

#### 동작에 미치는 영향

- 시간 안정화기는 아직 키포인트 모델이나 GUI에 연결하지 않았으므로 현재 수동 보정과 사용자 화면 동작은 바뀌지 않는다.
- 향후 자동 키포인트 보정을 연결하면 한 프레임의 오검출로 전술 보드 전체가 갑자기 이동하는 현상을 억제한다.
- 키포인트가 잠시 가려지면 제한된 기간 동안 이전 보정을 재사용하지만, 근거가 장시간 사라지면 좌표와 파생 지표가 자동으로 계산 불가 상태가 된다.
- 단순 평균이나 행렬 보간은 아직 하지 않는다. 이번 단계는 후보 채택·거부·만료·복구 상태를 명확하게 만드는 안전장치다.
- 기본 8m 점프와 30프레임 재사용 값은 합성 검증용 초기값이며 실제 영상 평가 후 조정해야 한다.

## 쿠팡플레이 녹화 검은 화면 원인 (2026-09-15)

- 증상: 쿠팡플레이 재생 화면을 녹화하면 결과 파일이 검게 나옴.
- 원인: 녹화(파일 저장)든 실시간 분석이든 두 방식 모두 화면 캡처 단계를 먼저 거친다. 차단이 캡처 단계에서 발생하면 저장 여부와 무관하게 동일하게 검게 나온다.
- 근거: Windows는 Desktop Duplication API 등에서 보호된(DRM) 영상 콘텐츠에 대한 캡처를 제한한다. 참고: https://learn.microsoft.com/en-us/windows-hardware/drivers/display/desktop-duplication-api
- 확인 방법: 프로그램의 '화면 영역 분석' 기능으로 쿠팡플레이 재생 화면을 실시간 캡처해본다.
  - 정상적으로 잡히면: 캡처 자체는 문제 없음 → 이전 녹화본이 검게 나온 원인은 녹화/저장 과정 쪽일 가능성이 큼 → 실시간 분석 진행.
  - 검게 나오면: 캡처 단계 자체가 차단된 것 → 현재 방식으로는 쿠팡플레이 재생 화면 분석이 어려움.
- 결론: 사용자 확인 결과 실시간 분석에서도 검게 나옴 → 캡처 문제로 확정. 쿠팡플레이의 보호 기능(DRM)에 의한 캡처 차단으로 판단됨.
- 후속 과제: 캡처 차단을 우회할 수 없다는 전제 하에, 대체 입력 경로(예: 비보호 소스, 별도 캡처 장치/HDMI 캡처보드 등)를 검토할 필요가 있음.
